2Open Challenges in Distributed Prefill Attention — and How iris Addresses Them
1
Pipelined KV transfer instead of AllGather — and fusing it with compute
Context parallelism splits the sequence across GPUs. The naive approach is to AllGather all KV before computing attention, which blocks compute behind a full synchronisation barrier. The more efficient approach — a pipelined ring transfer where each rank sends its KV chunk to the next while computing attention on what it already has — had not been done for attention. It had been done for GEMMs (iris examples 15–16), but attention has different structure: online softmax means you can't just split the work the same way.
iris answer — Phase 8, fused_ring_prefill_attn_kernel:

A single Triton kernel handles both the ring transfer and the flash attention in one CTA execution. At each ring step the kernel (a) sends the current KV chunk to the next rank via iris.store into a double-buffered sym-heap ring buffer, while simultaneously (b) computing flash_prefill_step on the KV received from the previous step. The online softmax state (acc, e_max, e_sum) accumulates across all ring steps without any intermediate normalisation, then a single final divide produces the output. No host-side communication calls. No separate communication kernel. The transfer and compute genuinely overlap within the same CTA.

Current limitation: The grid is currently (1, H) — one CTA per head — to avoid a per-head flag race when multiple Q-tile CTAs compete for the same signal. Phase 12 will fix this with a persistent kernel design (one CTA per SM, each owns a tile range), matching the pattern used in the fused GEMM+AllReduce kernels.
2
Sharing the KV cache block table across ranks in a peer-mapped way
In vLLM v0, prefill did not use a paged block table — the KV cache was contiguous, so an AllGather on raw tensors was straightforward. In vLLM v1, prefill also uses paged KV with a block table mapping logical block indices to physical block indices. Each GPU has its own local block table, and those physical indices are opaque to other ranks. You cannot simply call a remote memory read with a local block index — you need a routing layer that maps a global token position to the correct (rank, local physical block) pair.
iris answer — Phase 4, global block table:

The solution has two parts with different integration costs:

The routing metadata — genuinely compatible with vLLM v1:
build_global_block_table(local_block_tables, world_size) takes each rank's existing [batch, max_blocks] int32 block table and produces a global [batch, ws × max_blocks, 2] tensor where each entry is (owning_rank, local_phys_block_idx). Collect the local tables via dist.all_gather_object on the host (CPU, no GPU work), call the function, broadcast. The block allocator logic, physical indices, page size, and eviction policy are all unchanged.

The KV cache backing memory — requires a real change:
iris.load(ptr, my_rank, remote_rank, heap_bases) translates the pointer using heap_bases, which only works if the KV tensor was allocated on the iris symmetric heap — a virtual address region mapped identically on every GPU. vLLM's CacheEngine uses torch.empty(..., device="cuda"), which is regular CUDA memory. That pointer cannot be passed to iris.load.
# vLLM CacheEngine today: self.gpu_cache = torch.empty(num_blocks, block_size, H_kv, D, device="cuda") # Required for iris CP — backing memory from the sym-heap: self.gpu_cache = shmem.empty((num_blocks, block_size, H_kv, D), dtype=torch.float16) # ^^^^ one real change in CacheEngine # block allocator logic — unchanged # physical block indices — unchanged # build_global_block_table() — unchanged # page size, eviction — unchanged
What changes and what doesn't:

Component Needs changing?
Block allocator logic (free list, eviction, logical→physical mapping)No — unchanged
Block table format [batch, max_blocks] int32No — compatible as-is
Page size, physical block indices, evictionNo — unchanged
KV cache backing memory (CacheEngine allocation site)Yes — must use shmem.empty() instead of torch.empty()

Ring variant note: For the ring kernel the constraint is softer. KV is copied from the paged cache into flat sym-heap ring buffers at the start of each ring step. That copy reads from the KV cache using a regular tl.load — the same instruction any local kernel uses. So the ring variant could potentially stage from a non-sym-heap KV cache with only an extra copy step, without requiring the full CacheEngine change.
3
vLLM v0 was easy — v1 is where it gets hard
vLLM v0 prefill is contiguous — no block tables, so AllGather on raw tensors works. vLLM v1 uses paged KV for prefill too, which means all of challenge 2 applies. The existing ring attention literature largely sidesteps this because it assumes contiguous KV layouts.
iris answer — this is exactly the scenario iris targets:

The distributed_prefill_attn_kernel (Phase 5) is specifically designed around paged KV. The global block table walk happens inside the Triton kernel at the same point where a standard single-GPU paged attention kernel would do its local block table lookup. The only difference is the branch: local block → tl.load, remote block → iris.load. The paged structure is not abstracted away or staged into a contiguous buffer first — it is handled natively in the kernel's inner loop. This is what makes it a genuine v1-compatible solution rather than a v0-only workaround.

6Architecture — Peer-Mapped Block Table (Phase 4 Solution)
The Block Table Problem (vLLM v1 style)
# Each rank has its own local block table rank 0: block_table[b, i] → phys_block_idx # opaque to rank 1 rank 1: block_table[b, i] → phys_block_idx # opaque to rank 0 ... Problem: rank r needs KV from rank 0's blocks → can't just call iris.load with rank-0's local phys_idx → local block indices are not globally meaningful → need a routing layer that maps (global_token → rank + local_block)
The iris Solution: Global Block Table
# Build once on host at prefill dispatch time global_table = build_global_block_table( local_block_tables, world_size ) # shape: [batch, ws × max_blocks, 2] # global_table[b, i, 0] = owning_rank # global_table[b, i, 1] = local_phys_block on that rank Inside Triton attention kernel: owner = global_table[bid, token // PAGE_SIZE, 0] phys = global_table[bid, token // PAGE_SIZE, 1] kv_off = phys * stride_cb + slot * stride_cs + ... k_tile = iris.load(k_cache_ptr + kv_off, my_rank, owner, ctx.heap_bases) # ← RDMA
Ring Pipelining Architecture — fused_ring_prefill_attn_kernel
# world_size = 4, cur_rank = 2, tokens flow right-to-left Step 0: Use local KV (rank 2 chunk) │ Send local KV → rank 3 (ring buf A) flash_prefill_step(Q, K2, V2) │ iris.store() — overlaps compute [causal: self-attention] │ │ Step 1: Recv KV from rank 1 (buf A) │ Relay A → rank 3 (ring buf B) flash_prefill_step(Q, K1, V1) │ iris.store() while attending K1 [non-causal: rank1 < rank2] │ │ Step 2: Recv KV from rank 0 (buf B) │ (last step, no relay needed) flash_prefill_step(Q, K0, V0) │ compute only [non-causal: rank0 < rank2] │ │ Step 3: Skip rank 3 (rank3 > cur_rank=2) │ causal masking → skip [causal: future tokens] │ Normalize: out = acc / e_sum [fp16] │ Key property: iris.store relay in Step 1 overlaps with Step 1 attention compute → communication latency partially hidden behind compute

8Key Findings — Phase 13 Ablation (8× MI300X)
cp_allgather_nccl wins at large sequence lengths
At S_total=256K, cp_allgather_nccl achieves 18,509 TFLOPS — 93% of the local_flash ceiling (19,950 TFLOPS). NCCL AllGather at 250 GB/s is extremely fast (3.6 ms at 256K) relative to compute (54 ms), so the communication cost is nearly invisible. At large sequence lengths, context parallelism with NCCL AllGather is near-optimal.
iris ring transfer is the bottleneck — 1.8 GB/s vs NCCL 250 GB/s
comm_only_ring: 513 ms to transfer 256K KV at 1.79 GB/s effective bandwidth. comm_only_allgather: 3.6 ms at 251 GB/s. The iris ring transfer is 140× slower than NCCL AllGather for the same data. The ring is sequential (one rank-to-rank hop at a time), while AllGather is concurrent. This explains why cp_ring_fused at 256K takes 1,665 ms vs cp_allgather_nccl at 58 ms.
cp_ring_fused: 3.3× faster than cp_ring_unfused at 256K
Phase 12 (Option B) delivers a real speedup: cp_ring_unfused = 5,475 ms, cp_ring_fused = 1,665 ms at 256K llama3-8b. The 3.3× improvement comes entirely from replacing Python torch.einsum with ring_prefill_attn_step_kernel at full grid=(cdiv(S_local,BLOCK_Q), H). Both are still ring-transfer-bound — the attention compute is fast, the iris ring at 1.8 GB/s is slow.
TP is surprisingly slow — S_full queries overwhelm head-split benefit
tp at 256K: 434 ms (2,474 TFLOPS = 12% of ceiling). Each rank processes the full S_total=256K query sequence against H/8=4 KV heads. The O(S²) attention over 256K tokens dominates even without communication. CP (context parallelism) — splitting S — is strictly better than TP for long-context prefill.

9Phase 12 — Multi-CTA Race Fix Design
Current Problem (workaround in place)
Grid = (cdiv(S_local, BLOCK_Q), H) — multiple pid_q CTAs per head all spin-wait on the same per-head flag. When pid_q==0 resets the flag after receiving, all other pid_q CTAs on the same head see the flag cleared and stall indefinitely or proceed with stale data.

Workaround: Grid = (1, H) — one CTA per head iterates all Q-tiles sequentially. Correct but N× slower where N = cdiv(S_local, BLOCK_Q).
Option A — Persistent Kernel (preferred)
Single CTA per SM, each CTA owns a contiguous range of Q-tiles. Each CTA independently: (1) does the ring transfer for its assigned step (exactly once per step, no race), (2) iterates its tile range for attention compute.

Same design as gemm_all_reduce_ring_based.py in iris examples 15–16. Eliminates the race entirely. No cross-CTA synchronization needed. Full SM occupancy. Target: >50K tok/s at 256K.
Option B — Two-Phase Launch (safer fallback)
Separate ring transfer kernel (grid=(H_kv,), single CTA per KV head, handles all ring steps) from the attention kernel (grid=(cdiv(S_local,BLOCK_Q), H), multi-CTA, reads from already-transferred buffers). Unfused but race-free. Slightly higher launch overhead but eliminates all flag synchronization issues. Simpler to implement and test than Option A.
